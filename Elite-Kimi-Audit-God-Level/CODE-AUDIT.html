The short version

This is not amateur code. A 1:2 test ratio, a genuinely excellent storage engine, and comments that tell the truth put it well above that bar.

But one habit keeps the score down: when the codebase needs something it already has, it copies it instead of sharing it. The copies drift, and the drift becomes bugs. The fix is five shared building blocks, not a rewrite.

Appendix

Is the scoring repeatable, or gut feel?

Fair question. Honest answer: four of the six dimensions are count-based and re-runnable; two involve judgment. Here's exactly how each number was produced, so you can check any of it yourself from the repo root.

1. Duplication — repeatable

Method: enumerate every implementation of the same logic, by reading each subsystem end-to-end and confirming with search. Every cluster in this report lists its members with file:line, so "8 JSONL readers" is a list you can open, not an estimate. The 0–10 score maps off the count: 0–1 clusters ≈ 9–10, 2–3 ≈ 7–8, 4–6 ≈ 5–6, 7–10 ≈ 3–4, >10 with proven drift ≈ 2–3. This repo: 14+ clusters, several with drift → 3.3.

# spot-check one cluster yourself: grep -rn "torn" src/backend --include="*.ts" | grep -v test # the copied "torn line" catch grep -rn "pidAlive\|kill(pid, 0)" scripts src --include="*.mjs" --include="*.ts"

2. Failure handling — mostly repeatable

Method: count the swallow patterns mechanically, then classify by hand.

grep -rn "catch(() => {})" src --include="*.ts" --include="*.tsx" | grep -v test | wc -l grep -rn "catch {}" src --include="*.ts" | grep -v test | wc -l

The count (~45) is mechanical. The classification — "harmless torn-line tolerance" vs "the canvas-wipe bug" — is judgment, but each harmful one is cited with file:line and was verified by hand. The count anchors the score; the judgment only writes the commentary.

3. Coupling & module depth — semi-repeatable

Repeatable parts: import counts per file (components/index.tsx has 25), constructor parameter counts (MessageRouter takes 10), files over the repo's own 300-line rule (~15). Judgment part: deciding whether a file has "one job or seven" — e.g. tunnelModel/index.ts does lane math + mentions + HTTP + websockets + hooks + rooms + reconnect. The responsibilities are listed in the evidence sections so the judgment is auditable.

4. State discipline — semi-repeatable

Repeatable: module-level mutable bindings (12 found, mechanically), singleton stores (7, listed), unbounded caches (2, cited). Judgment: whether mutation is properly encapsulated.

grep -rn "^let \|^export let " src/frontend/lib --include="*.ts" | grep -v test

5. Testability — repeatable

Pure counting: test files vs source files (90 vs 178), test lines vs source lines (~1:2), per-area ratios (store engine 1.2:1; frontend components ~0.1:1 — the skew is the story). The only judgment is "could you test this without mocking the world", and the untestable cases (DashboardShell, 8 of 10 CLI scripts) are named.

6. Naming & honesty — judgment (admitted)

This one is a read-and-judge dimension. There's no grep for "does this name tell the truth". What keeps it honest: every deduction is cited (startDevServer() starts prod — desktop/main.cjs:60; two unrelated types both named AttentionItem; model.ts claims "pure" but does file I/O at :180-194), and every credit is cited too (the "recorded DRY debt" confessions, the ruling citations, zero TODO litter — that last one IS mechanical: grep -rn "TODO\|FIXME\|HACK" src | wc -l → 0).

Bottom line on method: the composite 5.5 is anchored on counts you can re-run. If you re-did this audit with different judgment calls, the score might move ±0.5 — it would not move from "duplication is the problem" to "everything is fine". The evidence lists are the report; the score is just their summary.
